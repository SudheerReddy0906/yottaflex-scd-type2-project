# Data Dictionary

## Source event CSV

| Column | Type | Required | Meaning |
|---|---|---:|---|
| event_id | string | Yes | Stable unique identifier for one source event |
| customer_id | string | Yes | Business key identifying the customer |
| customer_name | string | Yes | Customer name snapshot |
| city | string | Yes | Customer city snapshot |
| email | string | Yes | Customer email snapshot |
| effective_at | ISO-8601 timestamp | Yes | Business time at which this state becomes valid |

## customer_dimension

| Column | Type | Meaning |
|---|---|---|
| customer_sk | integer | Surrogate primary key generated by SQLite |
| customer_id | string | Customer business key |
| customer_name, city, email | string | Tracked attributes |
| effective_from | timestamp | Inclusive start of validity |
| effective_to | timestamp / NULL | Exclusive end; NULL for current row |
| is_current | 0/1 | 1 only for the current version |
| source_event_id | string | Event that introduced this version |

## Supporting tables

- `event_ledger`: accepted source events; primary key `event_id` makes replays idempotent.
- `quarantine`: rejected raw records and reasons.
- `pipeline_runs`: one operational record per execution.

## Assumptions

1. Each source event contains a complete customer snapshot, not a partial patch.
2. Timestamps are ISO-8601; timezone-naive timestamps are treated as UTC.
3. `effective_to` is exclusive.
4. Two different events for one customer at the exact same effective timestamp are ambiguous and rejected.
5. A repeated state is retained in the event ledger but does not create a redundant dimension version.
6. A late-arriving event causes that customer's timeline to be rebuilt from all accepted events.
